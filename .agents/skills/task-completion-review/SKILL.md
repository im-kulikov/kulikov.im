# task-completion-review: завершение задачи и накопление знаний

Две цели: **Quality Assurance** — проверить выполненную работу, и
**Knowledge Continuity** — сохранить подтверждённые знания, которые помогут
следующему агенту и владельцу. Это не бюрократическая процедура: отчёты
компактные, артефакты создаются только по подтверждённой необходимости.

## Как запускается

- ZCode: workspace skills авто-обнаруживаются из `<repo>/.agents/skills/`
  и вызываются Skill tool по имени (`task-completion-review`); в уже
  открытой сессии свежесозданный skill может отсутствовать в списке — тогда
  прочитать этот `SKILL.md` и следовать ему.
- Codex: `$task-completion-review`.
- Наличие директории само по себе обнаружение не гарантирует —
  обязательность закреплена правилом в корневом `AGENTS.md`.

## Разделение ответственности (не путать)

- **article-production** — конвейер статьи: intake, анализ фактов, brief,
  Markdown-статья, Telegram preview, генерация изображений, review package,
  publication workflow.
- **task-completion-review** (этот skill) — проверка выполненной работы,
  оценка качества, сохранение повторно используемых знаний, обновление
  agent-документации.
- Редакторский review конкретной статьи — этап article-production (шаг 12
  конвейера), а не этот skill. После изменения кода/скриптов внутри
  article-production применяется этот skill. При обычной подготовке статьи
  AGENTS.md и skills автоматически не переписываются — только при наличии
  подтверждённых полезных находок.

## Этап A — Self-Review

Проверить по фактам, опираясь на фактический `git diff` (не на собственное
описание изменений). Не утверждать, что проверки прошли, если они не
запускались:

- Все требования владельца выполнены? Незавершённые действия и побочные
  эффекты? Изменения вне scope?
- Соответствует ли реализация архитектуре проекта; переиспользованы ли
  существующие механизмы; не появились ли ненужные абстракции и дубли?
- Нет ли регрессий (затронутые тести запущены)?
- Локализация RU/EN не нарушена: у каждой не-черновой RU-страницы есть
  EN-двойник, на EN-страницах нет кириллицы (`tests/i18n.test.mjs`);
  блог — RU-only.
- Безопасность: секреты не добавлены (в коде, доках, diff); для editorial —
  `secrets-check.mjs` чист, правила обработки недоверенных ZIP соблюдены.
- Что реально запущено, что пропущено и почему, какие выводы — предположения.
- Открытые вопросы — выписать явно.

Очевидные самостоятельно исправимые ошибки чинятся сразу, затронутые
проверки повторяются.

## Этап B — Learning Brief

Промежуточный материал в рабочем отчёте (НЕ отдельный файл). Только реальные
наблюдения; пустые категории допустимы — писать `none`, не выдумывать
проблемы ради заполнения:

```text
Learning Brief
- Result:
- Problems -> fixes:
- User corrections:
- Unexpected findings:
- Failed assumptions:
- Repeat-risk knowledge:
- Suggested placement:
```

**User corrections — важнейший источник знаний.** Каждое существенное
исправление владельца — кандидат на сохранение (но не обязано становиться
отдельным правилом). Проверять, что решение ещё действует и не было
отменено позже; подтверждённые — в `.agents/docs/conventions.md`.

## Этап C — Risk-Based Review

Глубина review пропорциональна риску изменений.

- **Low** (небольшая правка текста, локальный CSS-фикс, обновление
  существующей документации): достаточно Self-Review и соответствующих
  проверок.
- **Medium** (несколько компонентов, responsive layout, Hugo templates,
  content pipeline): дополнительно — архитектурная согласованность,
  побочные эффекты, связанные компоненты.
- **High** (CI/CD, publication workflow, обработка недоверенных ZIP-архивов,
  security-sensitive логика, agent instructions/skills, влияющие на будущие
  задачи): углублённый review — архитектура, безопасность, корректность,
  регрессии, поддерживаемость, возможные ошибки в самих инструкциях.

Если доступны независимые review-агенты (например, skill `review-agent` или
Copilot pull-request-reviewer на PR — на PR #31 дал 20/20 валидных замечаний)
— использовать там, где это реально повышает качество (прежде всего High).
Если недоступны — не имитировать независимую проверку. Обязательное
количество reviewers не назначается без технического обоснования.
Замечания: собрать → проверить обоснованность → исправить подтверждённые →
аргументированно отклонить остальные. Критические проблемы не закрываются
формулировкой.

## Этап D — Knowledge Review

Центральная часть. Для каждого кандидата из Learning Brief ответить:

1. Может ли проблема повториться?
2. Снизит ли знание риск будущей ошибки?
3. Сэкономит ли оно время следующему агенту?
4. Не очевидно ли оно из исходного кода?
5. Не является ли оно слишком частным?
6. Не противоречит ли существующим инструкциям?
7. Есть ли подтверждение (факт, тест, наблюдение)?

Приоритет действий (минимальное изменение лучше):

1. Ничего не менять.
2. Исправить существующую инструкцию.
3. Обновить существующий skill.
4. Обновить существующий документ.
5. Создать новый документ.
6. Создать новый skill — только при доказанной необходимости.

**Сохранять:** неочевидные ограничения архитектуры; подтверждённые
conventions; исправления владельца; повторяющиеся ошибки; неудачные
гипотезы, которые могут повториться; ограничения инструментов и CI;
особенности Hugo и i18n; особенности responsive layout; ограничения image
pipeline; требования безопасности; проверенные способы диагностики;
неочевидные зависимости между компонентами.

**Не сохранять:** очевидное из кода; временные значения; случайные ошибки
одной сессии; непроверённые предположения; длинные истории отладки без
практического вывода; секреты и приватные данные; дубли существующих
инструкций.

## Этап E — Knowledge Improvements

Правильное место хранения:

- **`AGENTS.md`** — только обязательные правила, краткая информация о
  проекте, ссылки на документацию, правила применения skills. Без длинных
  troubleshooting-разделов.
- **`.agents/docs/`** — подтверждённые знания о проекте: архитектура,
  conventions, development, editorial workflow, ограничения и процедуры.
  Предпочитать обновление существующих файлов.
- **`.agents/skills/`** — повторяемые процедуры. Проектные факты, уже
  описанные в `.agents/docs/`, внутрь skills не копировать — ссылаться.

**Анти-рекурсия:** улучшения документации/skills, сделанные внутри этого
цикла, входят в тот же completion cycle. Их нужно проверить (этап F), но
полный новый review на них не запускается. Новый цикл — только для новой
самостоятельной задачи.

## Этап F — Validation

- Код/конфиги/шаблоны: `HUGO_BIN=$PWD/tmp/bin/hugo npm test`; для UI —
  затем `npm run test:e2e` (у него нет pretest — сначала `npm test`).
  Editorial-скрипты: `node .agents/skills/article-production/scripts/test.mjs`.
- Только документация/skills: тяжёлые проверки не запускать без
  необходимости, но проверить — корректность Markdown и frontmatter,
  относительные ссылки и пути, отсутствие дублирования и противоречий,
  соответствие реальному проекту, отсутствие секретов, отсутствие
  изменений вне scope.
- Практическая польза: какую проблему решает улучшение; сможет ли
  следующий агент воспользоваться им без расследования.

## Этап G — Quality Gate

Обязательные пункты: требования выполнены; Self-Review проведён; Learning
Brief подготовлен; Risk-Based Review соответствует риску; Knowledge Review
выполнен; необходимые знания сохранены; лишняя документация не создана;
проверки выполнены или ограничения явно указаны; нет незакрытых критических
проблем; `git diff` соответствует scope. Существенная проблема, найденная
на гейте, исправляется с повтором затронутых проверок — задача не
объявляется завершённой при известной критической проблеме.

Коммит — только с явного разрешения владельца (текущее правило проекта);
фазовые чекпоинты владельца имеют приоритет.

## Этап H — Final Report

Краткий, в формате:

```text
Task Completion Review

Result:
- ...

Validation:
- ...

Issues fixed:
- ...

Knowledge updates:
- Updated: ...
- Reason: ...

Open questions:
- ...
```

Если сохранять нечего: `Knowledge updates: none — no reusable findings.`
Это нормальный результат, а не ошибка процесса. Длинный Learning Brief
пользователю не выводится, если в нём нет практически полезной информации.

## Запрещено

- Фиктивные отчёты и имитация независимой проверки.
- Артефакты ради артефактов, бесконечные review.
- Выдача непроверенных изменений за успешные.
- Коммит при незакрытых критических проблемах.
- Сохранение непроверённых предположений как правил.
